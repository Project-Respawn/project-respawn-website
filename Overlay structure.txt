# Project Respawn
# Overlay Engine
## Technical Design Specification

Version: 0.2.0 Foundation

---

# Purpose

The Overlay Engine is the presentation layer for Project Respawn.

Its purpose is to receive standardized events from any supported platform and render them as beautiful, animated widgets inside OBS.

The Overlay Engine should never contain platform-specific business logic.

Instead, every external system converts its own events into a common Overlay Event which the engine can display.

This separation makes the system completely platform agnostic and future proof.

---

# Vision

Most streaming software treats every alert individually.

Follow Alert

Subscription Alert

Raid Alert

Donation Alert

Prediction Alert

Goal Alert

All separate systems.

Project Respawn takes a different approach.

Everything becomes an Overlay Event.

The Overlay Engine simply renders Overlay Events.

This allows the same engine to support Twitch, Discord, YouTube, Kick, the Project Respawn website and future integrations without rewriting the overlay.

# Responsibilities

Overlay.vue

Responsible only for displaying widgets.

No business logic.

No socket logic.

No Twitch logic.

Overlay.js

Controls the Overlay Engine.

Initialises services.

Receives overlay events.

Controls the active widget.

Nothing more.

OverlaySocket

Responsible only for communication.

Connect

Reconnect

Disconnect

Receive JSON

No Twitch logic.

No widget logic.

OverlayEventFactory

Responsible for converting raw events into Overlay Events.

Every platform should produce exactly the same output.

QueueService

Controls display order.

Ensures only one overlay is displayed at a time.

AnimationService

Provides reusable animation methods.

ThemeService

Provides colours, themes and styling.

Widgets

Responsible only for presentation.

# Overlay Event

Every event inside the engine should use the same format.

```javascript
{
    id: "",

    type: "",

    widget: "",

    priority: 0,

    title: "",

    subtitle: "",

    message: "",

    username: "",

    icon: "",

    image: "",

    sound: "",

    animation: "",

    theme: "",

    duration: 5000,

    payload: {}
}
```

No widget should receive Twitch data directly.

Every widget receives an Overlay Event.

# Design Principles

Single Responsibility

Every file should do one thing.

Loose Coupling

Services should not know about widgets.

Widgets should not know about sockets.

Overlay should not know about Twitch.

Platform Agnostic

Everything should work with any platform.

Scalable

New widgets should require little or no modification to existing systems.

Readable

Prefer simple code over clever code.

Reusable

If code is repeated, move it into a service.

# Rules For Future Development

The following rules should be followed throughout the lifetime of the Overlay Engine.

1.

Never place platform-specific logic inside the Overlay Engine.

The Overlay Engine should never know whether an event originated from Twitch, Discord, Kick, YouTube or any future platform.

2.

Never bypass the Overlay Event Factory.

Every external event must be converted into a standard Overlay Event before entering the Queue.

3.

Every service should have one responsibility.

OverlaySocket handles communication.

OverlayEventFactory converts events.

QueueService manages display order.

AnimationService manages animations.

ThemeService manages themes.

Widgets display content.

Nothing more.

4.

Widgets should never communicate directly with sockets.

Widgets should only receive Overlay Events.

5.

Avoid hard-coded behaviour wherever possible.

If a feature can become configurable in the future, it should be designed with that in mind.

6.

Never rewrite the Overlay Engine without updating this specification.

The documentation should always represent the current architecture.

7.

Complete one system before starting another.

Foundation first.

Features second.

Optimisation third.

8.

If implementing a new feature requires modifying several existing services, stop and review the architecture.

The goal is to extend the engine, not repeatedly modify it.
