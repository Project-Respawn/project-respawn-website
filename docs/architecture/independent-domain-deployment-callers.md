# Restricted deployment callers for independent domains

An independent product stack needs three separate identities: a security custodian, a restricted deployment caller and a CloudFormation execution role. Runtime roles form a fourth, narrower layer. Creating an execution role and an unattached caller policy does not establish a usable deployment caller.

The custodian applies separately authorized IAM changes. It must not be substituted for the restricted product caller. The caller assumes a dedicated role with trust restricted to the approved operator or deployment workflow; use short-lived credentials without writing them to disk. Apply its reviewed policy as both identity authority and permissions boundary. Reuse an existing policy only after reviewing every semantic change and its current attachments.

Scope product CloudFormation orchestration to the exact account, region and stack name, with the physical stack suffix wildcard needed for first creation. Permit the required inspection and change-set actions, not arbitrary CreateStack/UpdateStack/DeleteStack or account-wide listing. Bind change-set creation to the reviewed template URL and execution role. PassRole must identify that role exactly and require CloudFormation as the destination service. The caller receives only exact deployment-object reads; it does not administer Lambda/API Gateway, change IAM, access business storage or decrypt KMS data.

Validate the proposed policy and trust, including positive lifecycle/reads/PassRole cases and explicit negatives for LegacyPlatform, other domains and production. Inspect the AWS-generated security change set before its separately authorized execution. Read back the installed trust, attachments and boundary, assume the role and repeat actual-principal checks. Use the assumed caller for product preparation, inspection, execution and monitoring.

When API Gateway first creation requires temporary regional execution authority, retain protected-ID exclusions and a reviewed expiry with at least the agreed rollback/lockdown reserve. After product creation, verify actual API ownership and tags, bind exact-ID authority, inspect the security-only update, install it and verify both execution identity and boundary. Preserve the caller extension when deriving a lockdown template from an older security template. Deny CreateApi and every other API before runtime acceptance.

Team Hub is the concrete example: one new caller role plus modification/reuse of the existing PreparationCaller policy, for five security resources total. Its exact product template and ZIP use AES256 despite the bucket's KMS default. The execution role was not broadened. The [Release 1 report](team-hub-2b2-read-path-release1-2026-10-05.md) records candidate hashes, gates, actual role use, lockdown, authentication, runtime evidence and protected baselines. [Implementation and operational constraints](../../infrastructure/security/team-hub-Ntgre-deploy-caller/README.md).

This pattern complements the [Domain Architecture Standard](project-respawn-domain-architecture-standard.md); it does not authorize deployment of another domain or reuse of Ntgre-specific ARNs in another environment.
