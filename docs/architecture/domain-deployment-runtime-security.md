# Domain deployment and runtime security standard

Approved architectural decision: 4 October 2026. This supersedes the earlier requirement to prove perfect per-resource API Gateway execution-role isolation before Tournament Release 1. Historical policies, unsuccessful deployments and diagnostic evidence remain unchanged.

**Runtime isolation: STRICT. Deployment execution isolation: SERVICE-LEVEL / PRACTICAL. Production / Legacy stack protection: MANDATORY.**

Project Respawn has one shared Core identity authority per environment and independent product domains. Tournament, Team Hub, Creator, Commerce, Community/Events, Applications/Intake and Investor consume shared Cognito identity; consuming identity does not transfer Cognito ownership. Each reviewed substantial domain should own its frontend boundary, API/client, functions, business data, sibling CloudFormation root and release lifecycle. Small modules do not automatically justify another root. Existing LegacyPlatform resources remain in place until separately authorized migration.

A domain deployment caller may operate only its allowlisted stack using its designated CloudFormation service role and approved template. The CloudFormation execution role can have practical permissions for necessary deployment services. It is not the product runtime identity. Do not install AdministratorAccess or PowerUserAccess. Use explicit service permissions, supported resource scopes, region/environment validation, immutable artifacts and complete change-set inspection. Other-domain role implementations and migrations are not authorized by this standard.

A runtime identity receives only domain-owned runtime/data access. Cross-domain communication requires explicit APIs/contracts. No implied Team data, Creator secrets, Commerce data, infrastructure administration or Cognito administration is granted. A permissions boundary caps identity-policy permissions; it does not itself grant runtime permissions. [AWS boundary evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html).

## Limits and mandatory operating controls

The API permission is not perfect account-wide tenant isolation. Existing API-ID denies do not protect every future API or every account-level resource/custom-domain mapping. RequestedRegion does not distinguish environments sharing an account/region. API Gateway ARNs omit account IDs. Tags are ownership evidence, not a universal hard authorization boundary. No stronger guarantee is claimed. Do not use this service role through another stack, run direct ad hoc API mutations, or substitute an unrestricted template.

The unchanged Deploy boundary accepts only the hash-addressed template URL. Verify both published object bytes before preparation because an S3 key is not inherently immutable. Pin the account, region, stack ARN, original API ID and candidate manifest. Inspect all changes and reject replacement/deletion, stateful resources, unexpected resources or production targeting. Verify LegacyPlatform's complete resource/template identity, protected IDs, monitored Lambda hashes and timestamp before/after. These are mandatory operational controls, supplementing IAM. [AWS service-role guidance](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-iam-servicerole.html).

Simulations and Analyzer inclusion checks are evidence, not proof of successful service execution. Preserve raw simulator discrepancies and use independent grant-inclusion checks with sensitive deny controls. The authorized deployment is the live lifecycle test. Any deployment resource failure ends the attempt: allow rollback, collect evidence and stop without permission patches or retries.
