# Team Hub staffing and multiple-game expansion

Implementation scope: proposed independent Team Hub structure contract, offline validation and subsequent UI/API candidates. Existing deployed API permits one COACH and League only; this catalogue does not claim those deployed restrictions have changed.

Owner: Team Hub / squad membership, staff appointments and game-specific lineup. This is an extension of the existing independent Team Hub root, Operational/Journal authority and secured Core contracts. Do not add staff models to LegacyPlatform or create a new root, API, Cognito pool or table per game. A team remains a game-specific squad; the organisation may operate several squads.

Core staff: one Head Coach, one Assistant Head Coach, one Position Coach per configured game position and two Analysts. Retain the existing Team Manager role. Optional additions: Performance Coach, Strategic Coach, Scout and Team Coordinator. Positions are optional vacancies, not required headcount. A job title is not a permission grant.

Security: retain canonical Cognito identities and fresh server-side Core administrator decisions. The owner has requested configurable staff permissions instead of a fixed Analyst access class. The sole Manager controls the team, can revoke the Head Coach and can transfer ownership to an active member. Head Coach has team-operational control and can configure staff grants, but cannot revoke, replace, transfer or alter the Manager. Global Admins can inspect teams, delete teams and replace Managers. Team deletion is reserved for global Admins. Assistant coaches and other staff receive no management authority merely from their title. Neither delegates nor browser inputs may appoint themselves Head Coach or Manager. Only the Manager or global Admin may appoint/replace Head Coach; the Head Coach may manage subordinate appointments. Appointment endpoints must explicitly enforce this reserved-position rule, independently of staff.manage. Permissions governance cannot be delegated to subordinate staff. Private coach notes remain author-scoped and disabled where the accepted rollback contract requires it. Revocation atomically disables membership, appointments, roster and grants; retain personal pool data and prohibit revoked users from reading team data or receiving team-scoped benefits.

`structure/permissions.mjs` is an offline proposed policy model, not an installed authorization boundary. Manager and Head Coach can set/revoke per-member grants for roster, membership, pools, shared reviews, settings and subordinate staffing. Analysts default to no competitive-data access until granted. Ownership transfer changes one authoritative Manager pointer in the same transaction; the former Manager retains membership but loses inherent Manager privileges. Require recipient confirmation in the future transfer UI, active-recipient validation, expected owner/membership versions, authority/epoch condition, idempotency and audit. Never use the model's caller-provided platformAdmin flag directly: the service must derive it from current Core authorization. Current tests cover hierarchy, granular grants, revocation, transfer, staff capacities and game capability gating; they do not prove live storage or transactional integration.

Games: separate lineup templates from staffing and permission classes. League keeps TOP/JUNGLE/MID/ADC/SUPPORT. Other proposed games use generic player-position slots initially so League roles and champion-pool tools do not leak into them. The three-substitute limit remains. These are product templates, not claims about every tournament's rules. The API must explicitly advertise each supported game before the website offers creation. Existing teams keep their current game and roster; no automatic conversion.

State/contract implications: introduce explicit staff position/specialty metadata tied to an active membership. Existing COACH projects as Head Coach for compatibility. Multiple staff appointments require a reviewed contract revision because v1 currently revokes the previous Coach and strictly rejects unknown role fields. Every mutation must keep server-side Core decisions, actual authority/epoch conditions, current membership and target revisions, transactional capacity, idempotency and audit. Analyst permissions must be settled before enabling the API.

Resource accounting: proposed storage in the existing Team-owned Operational table and Journal; no new stateful resource or IAM grant is justified. Actual API-route/integration resource deltas must be synthesized and reviewed when an API candidate is prepared; zero additions must not be assumed before synthesis. No live changes are authorized or performed by this preparation.

Frontend: retain the lazy Team route. Coaching/Staff gets a distinct section from player lineup and Members. Never render a job title as saved until acknowledged by the backend. Do not expose unavailable game choices or pretend two Analysts can be assigned through the existing single-Coach API.

The [permission-system implementation](team-hub-permission-system.md) now provides an offline server/client save path and feature table for existing operational capabilities, protected by a default-off runtime release switch. This does not implement additional staff appointments, ownership transfer or additional game squads. Those remain separate contract work. Live saving requires a reviewed deployment; the current deployed API still returns no permission contract.

Delivery: catalogue/capacity/visibility and proposed authorization-model tests first; implement and verify the v2 service/storage projections, reserved appointment controls and compatibility; synthesize the isolated runtime/product candidate; separately authorize deployment; then bind frontend staff assignment and complete multi-persona acceptance. No production publication or migration is implied. Preserve all accepted v1 pins and existing records for state-aware rollback. The existing v1 singleton-Coach endpoint cannot safely persist these staff assignments; do not display these proposed controls as functional until the coordinated backend contract is available.
