# Application storage backend — phase 1

## Existing architecture inspected

Project Respawn uses one Amplify Gen 2 data schema and a shared `myFunction` Lambda for custom AppSync operations. Generated model access is intentionally narrower than custom-operation access: sensitive models are readable only by their owning backend resource, while authenticated custom queries resolve the caller's Cognito identity and effective permissions from `PermissionDefinition` and `GroupPermission`. `PermissionAuditEvent` is the existing management-audit convention. The canonical local environment is the protected `Ntgrestage8` sandbox described in `local-amplify-development.md`.

The current Creator Programme form uses pathway key `creator`. Competitive pathway keys remain stable in `applicationPathwayAvailability.js`, but all four competitive routes are closed. The current public form deliberately has no persistence call. Admin application pages consume a transport-shaped adapter and the fictional `APP-DEMO-0001`; this phase does not replace that adapter or copy the fixture into backend data.

## Proposed and implemented data design

`ApplicationSubmission` is the aggregate root. Its UUID and non-sequential `PR-…` reference are generated by the server. It stores pathway/form/consent versions, applicant and creator names, normalized contact email, trusted verification provenance, the controlled workflow status, a separate write state, submission/source timestamps, current-review placeholder data, idempotency/test-run tags, and safe audit metadata.

Related records preserve queryable, ordered, versioned facts:

- `ApplicationAnswer` belongs to one submission and snapshots stable question/section keys and labels, answer type, structured JSON value, optional safe display value, order, and form version.
- `ApplicationCreatorProfile` belongs to one submission and stores platform, optional Other label, public handle/URL, primary/active flags, content types, relationship-to-community information, and order. It never accepts credentials or tokens.
- `ApplicationSchedule` belongs to one submission and retains the applicant's IANA zone with recurring local day/start/end values, variation flags, optional profile association, next public stream, viewing URL, notes, and order.
- `ApplicationAuditEvent` belongs to one submission and contains safe event metadata only—never contact email or complete answers.
- `ApplicationIdempotency` is keyed by a one-way digest of the trusted idempotency key and stores the payload digest, operation state, aggregate ID, and safe result. A future retention job may remove terminal records after the documented retention period; active or failed writes must not be removed blindly.

Each of the six models has a fail-closed rule with an empty operation set because this Amplify transformer requires every model to declare a rule. It grants even `SuperAdmin` no direct model operation. The schema-level resource grant separately lets the shared Lambda query or mutate them. There is no guest, owner, authenticated-model, group-model, or API-key CRUD operation; the installed Gen 2 schema API supports resource grants at schema scope rather than model scope.

## Submission boundary and validation

`storeTrustedApplicationSubmission` is a custom AppSync command restricted at the schema boundary to `SuperAdmin`, then checked against `applications.storage.trusted`. It accepts one JSON command plus an idempotency key. It rejects client-owned IDs, references, status, review state, timestamps, audit identity, and verification flags. The trusted caller must supply an approved verification provenance (`trusted-test` in this phase); this is not a public-email verification mechanism and the public form does not call it.

The active combination is `creator` + `creator-v1` + `creator-consent-v1`. Historical competitive keys are recognized but closed, and unsupported combinations fail closed. Validation covers required snapshots and types, field and collection limits, email normalization, HTTPS public URLs, credential-shaped fields, IANA zones, recurring local times, consent, and unexpected input fields. Script text remains ordinary stored text; downstream Vue rendering must continue using text interpolation rather than raw HTML.

The canonical initial visible workflow status is `AWAITING_REVIEW`. During persistence the separate write state is `PENDING_WRITE`; only after all expected children and completion audit exist does it become `COMPLETE`. Failures become `FAILED_WRITE` and are excluded from admin list/detail queries.

## Partial writes and idempotency

Amplify model operations do not provide a transaction spanning all related tables, so this implementation does not claim atomicity. The service creates a deterministic idempotency row, creates/updates the aggregate as `PENDING_WRITE`, writes deterministic child IDs, verifies expected child counts, records safe audit events, and finally marks the aggregate `COMPLETE` with status `AWAITING_REVIEW`.

An injected failure is caught, a best-effort safe failure audit is written, and only that aggregate is marked `FAILED_WRITE`. Retrying the same key and payload removes only deterministic children belonging to that failed aggregate before rebuilding it. Unrelated records are never scanned and deleted. The same key and same canonical payload returns the prior successful safe result; the same key with a different payload is rejected. Conditional creation of the digest-keyed idempotency row elects one writer. Contenders re-read the row and return the single logical result; a bounded in-progress response is safe to retry.

## Protected reads and transport contracts

`listAdminApplications` and `getAdminApplication` require `applications.read`. The list accepts bounded page size, opaque next token, search, status/pathway filters, and ascending/descending submission-date order. It returns summaries only and never contact email or submitted answers. The detail mapper returns ordered answer snapshots, profiles, schedules, protected contact information, consent/submission metadata, and safe audit entries rather than generated storage shapes.

| Caller | Direct model CRUD | Trusted store command | Admin list/detail |
| --- | --- | --- | --- |
| Guest | Denied | Denied | Denied |
| Authenticated member | Denied | Denied | Denied |
| Staff without explicit permission | Denied | Denied | Denied |
| Reviewer (phase 1) | Denied | Denied | Denied |
| Admin with `applications.read` | Denied | Denied | Allowed |
| SuperAdmin with `applications.storage.trusted` | Denied | Allowed | Only with `applications.read` |
| Shared backend Lambda | Aggregate persistence only | Handler implementation | Handler implementation |

The initial catalog assigns `applications.read` to SuperAdmin and Admin and `applications.storage.trusted` only to SuperAdmin. Assignments remain configurable and are enforced at runtime; group membership alone does not bypass a missing assignment.

## Testing strategy and sandbox safety

Pure unit tests use an in-memory model client to cover validation, round-trip fidelity, authorization, query/filter/pagination behavior, idempotency/concurrency, injected partial failures, targeted recovery, safe errors/log metadata, and reference uniqueness. Static contract tests assert model relationships and the absence of public/authenticated model CRUD. Amplify TypeScript and existing guard suites protect shared behavior.

The sandbox integration runner is explicitly pinned to `Ntgrestage8`, generates a unique test-run ID, invokes the trusted command with a test-only provenance, reads through the admin boundary, checks replay/filter visibility and an intentional failure, and deletes only exact IDs returned for that run. If suitable authenticated identities or current generated operations are unavailable, the sandbox layer is reported as blocked; authorization is never weakened to make it run.

Production is outside this phase. No public form connection, review/scoring state machine, booking/induction persistence, Outlook integration, email delivery, or production deployment is included.
