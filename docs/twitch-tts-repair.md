# Twitch TTS local repair

Date: 2026-09-25. Status: implemented locally in the website and sibling Respawn Twitch Bot repositories; not deployed. The [investigation](twitch-tts-investigation.md) describes the original failures.

## Behavior

- A matching channel-points redemption now produces canonical `tts.requested` with sanitized text through the bot's signed runtime client. Existing reward-alert delivery remains independent. The new `RESPAWN_CANONICAL_TTS_DELIVERY_ENABLED` flag controls canonical speech delivery; production and staging task definitions set it to true for a future rollout. The existing alert flag is unchanged.
- Runtime deduplication gives speech its own derived-output key, so a reward alert cannot consume its delivery claim. Existing alert claim keys remain compatible. Retries preserve Twitch message identity.
- The canonical publisher accepts an enabled, visible TTS widget subscribed to `tts.requested`, checks the Brand's saved TTS enable setting and rejects empty text. Existing publication, Workspace, Brand and lease checks remain in place.
- The Browser Source uses one shared speech queue across TTS widgets. It suppresses duplicate IDs, preserves event order, applies saved voice/rate/pitch/volume/length settings, and stops on source teardown or global TTS disable. Playback metadata logs distinguish queued, started, ended and failed speech without logging message text. Speech is generated by the browser's speech engine; no cloud voice service is added.
- Settings expose the saved enable switch. Test feedback distinguishes zero connected sources, failed sends and successful transport delivery; transport success is not proof of audible playback. The page links to published Browser Sources and labels its history as local previews. The old `/tts-overlay` renderer remains unsupported for this flow.

## Architecture and deployment boundary

Owner: Creator Tools / Twitch overlays; the bot owns EventSub ingestion. This repairs an existing module and its contracts, rather than introducing a new domain. It retains existing LegacyPlatform handlers, configuration storage and the independently deployed Twitch runtime service. No new root or nested stack is warranted.

Shared contracts remain the signed integration lease, existing Workspace/Brand authorization, publication credential and canonical overlay event schema. Viewer input is untrusted content, sanitized before delivery. Management writes continue to require existing creator authorization; publication readers use the existing source credential. Diagnostics belong to the Twitch/overlay runtime and omit message bodies.

Source-level resource delta: zero tables, indexes, functions, resolvers, data sources, IAM grants, log groups or custom providers. Only existing Lambda code and the existing runtime task environment change. No schema or construct identity changes, data migration, Cognito changes or sandbox replacement. Root/template resource budgets must still pass the repository synthesis guard; no budget baseline is refreshed for this repair.

Frontend modules load through existing creator/source routes. The queue adds no SDK or dependency and does not change route guards. Existing Amplify code remains subject to that root's deployment lifecycle; a nested handler is not an independent deployment promise.

Future rollout order, requiring separate deployment authorization: deploy the existing backend handlers using the publisher/runtime changes, deploy the website, then release the matching bot image and task definition with the TTS flag. Validate in the intended environment before production. To roll back canonical ingestion, disable the new task flag and restore the previous image through the normal pipeline; this restores prior behavior and does not make the legacy renderer functional. No state migration is required.
